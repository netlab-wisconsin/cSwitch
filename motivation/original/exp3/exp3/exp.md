## Naming
* The precise term we will use is:
    * `L2-resident synchronized cache-to-cache bandwidth`
* In figures/tables, we may shorten this to:
    * `L2-L2 sync bandwidth`
* Reason:
    * the data is kept in a private-cache-sized working set and moves through the coherence path between two pinned cores
    * this is more precise than the broader phrase `core-to-core bandwidth`

## Measurement Decision
* We will **not** use single-cacheline CAS as the primary exp3 metric.
    * single-line CAS mostly measures lock ping-pong / ownership latency
    * it does not expose enough steady-state throughput
* We will use **multi-cacheline cache line bouncing** as the primary exp3 benchmark.
    * producer thread writes a payload spanning many cache lines
    * consumer thread reads or validates that payload after a sequence handoff
    * a small control flag / sequence counter on separate cache lines is used only for synchronization
    * payload bytes are counted once, from producer to consumer
* We may keep **multi-cacheline CAS** as a secondary comparison mode later.
    * useful as a stress / ownership-transfer variant
    * not the main number reported in exp3

## Fixed Benchmark Definition
* Primary tool:
    * extend `/home/seunghyun/core-to-core-latency` with a new benchmark, e.g. `--bench 4`
* Peak-oriented alternative:
    * `/home/seunghyun/core-to-core-latency --bench 5`
    * duplex / double-buffer streaming variant
    * reports aggregate full-duplex useful bandwidth
* Benchmark style:
    * two threads pinned to a selected pair
    * synchronized producer-consumer handoff
    * payload made of many 64B cache lines
    * one-way effective bandwidth computed as `payload_bytes / elapsed_time`
* Payload size:
    * default payload per round: `256 KiB`
    * reason: large enough to amortize sync overhead, still comfortably below the per-core `1 MiB` L2 size on this machine
* Synchronization:
    * producer writes payload, then publishes a sequence value
    * consumer waits on the sequence value, reads the payload, then acknowledges completion
    * control variables must live on separate cache lines from the payload
* Repetitions:
    * use `10` outer repeats per condition, aligned with exp2
* Reported result:
    * `pair, traffic_type, traffic_threads, payload_kib, bandwidth_runs, mean_bandwidth_gibs, stdev_bandwidth_gibs`

## Tool Choice
* Primary:
    * `core-to-core-latency` extension
    * best fit because it already pins explicit core pairs and already measures coherence-path interaction directly
* Validation only:
    * `likwid-perfctr`
    * use `L2` / `CACHE` groups on a subset of runs to confirm the chosen payload stays mostly out of DRAM
* Not primary:
    * `Intel MLC`
    * practical reason: it is Intel-oriented, not installed here, and the quantity we need is synchronized pairwise cache-line handoff throughput rather than a generic memory-bandwidth number
* Not primary:
    * `pmbw` / `likwid-bench` stock kernels
    * good for parallel cache/RAM streaming bandwidth
    * not a direct measure of pairwise synchronized cache-line bouncing

## Validation
* Before full exp3 runs, do one short size sweep on the no-traffic case:
    * `64 KiB`, `128 KiB`, `256 KiB`, `512 KiB`
* Goal of the sweep:
    * make sure `256 KiB` is already in the throughput plateau region
    * if not, move the fixed payload to `512 KiB`
